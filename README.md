# RPC-фреймворк

Небольшой RPC-фреймворк на Java 21. Клиент вызывает методы интерфейса через
Dynamic Proxy, сервер выполняет их через Reflection. Между ними — TCP-сокет
и JSON. Из библиотек используются Jackson и JUnit 5.

## Запуск

Сборка с тестами:

```shell
mvn clean verify
```

В первом терминале запустить сервер:

```shell
mvn exec:java "-Dexec.mainClass=example.ServerMain"
```

Во втором терминале запустить клиент:

```shell
mvn exec:java "-Dexec.mainClass=example.ClientMain"
```

Это два отдельных процесса JVM. По умолчанию используется `localhost:9090`.
Другой порт можно передать обеим командам через `"-Dexec.args=9091"`.
Для остановки сервера нажать Ctrl+C.

Клиент выводит каталог и расписание первого плана, добавляет временную копию
плана и удаляет её. Для просмотра второго плана:

```shell
mvn exec:java "-Dexec.mainClass=example.ClientMain" "-Dexec.args=9090 2"
```

## Каталог тренировочных планов

При запуске сервера доступны два тренировочных плана по три дня. Это вымышленные
данные для демонстрации программы. Они находятся в `example/DemoPlans.java`.

`TrainingPlan` содержит номер, название и расписание по дням.
`Exercise` содержит название упражнения, число подходов и повторений,
а также вес в килограммах. Если вес не указан, `weightKg` равен `null`.

| Метод | Результат |
| --- | --- |
| `findAll()` | Список всех планов |
| `findById(id)` | План по номеру или `null` |
| `getSchedule(id)` | Дни и списки упражнений; ошибка, если плана нет |
| `saveAll(plans)` | Добавляет планы; существующий номер заменяет прежний план |
| `delete(id)` | Удаляет план; отсутствующий номер ничего не меняет |

Планы хранятся в `LinkedHashMap` в памяти сервера. Перезапуск восстанавливает
исходные два плана. Порядок планов и дней сохраняется.

`PlanService` наследует `findAll()` и `findById()` от `PlanCatalog` — пример
дополнительного пункта B. Метод `getSchedule()` возвращает
`Map<String, List<Exercise>>` — пример пункта D.

## Использование

Интерфейс и DTO должны быть доступны обеим JVM. Реализация нужна только серверу.

Сервер:

```java
RpcServer server = new RpcServer(9090);
server.register(PlanService.class, new PlanServiceImpl());
server.start();
```

В `PlanService` стоит аннотация `@RpcService`, поэтому в `ServerMain`
используется короткая регистрация:

```java
server.register(new PlanServiceImpl());
```

Эта перегрузка регистрирует все помеченные интерфейсы реализации, включая
интерфейсы её родительских классов и интерфейсов. Если помеченных интерфейсов
нет, выбрасывается `IllegalArgumentException`. Обе перегрузки доступны до `start()`.

Клиент:

```java
PlanService plans = RpcClient.create(PlanService.class, "localhost", 9090);
System.out.println(plans.findAll());
System.out.println(plans.getSchedule(1));
```

`create()` только создаёт прокси. Каждое обращение к методу открывает новое
соединение. `equals()`, `hashCode()` и `toString()` выполняются локально,
как у `Object`.

Таймаут по умолчанию — 5 секунд. Его можно задать четвёртым аргументом:

```java
RpcClient.create(PlanService.class, "localhost", 9090, Duration.ofSeconds(2));
```

Таймаут отдельно применяется к подключению и чтению ответа. Он не останавливает
метод на сервере. Допустимо положительное значение до `Integer.MAX_VALUE`
миллисекунд; значения меньше миллисекунды округляются до одной миллисекунды.

Конструктор сервера сразу занимает порт. Порт `0` выбирает свободный,
его номер возвращает `port()`. Сервисы регистрируются до `start()`.
`start()` блокирует поток и обрабатывает соединения по очереди. `stop()`
закрывает слушающий сокет и освобождает порт. Уже начатая обработка запроса
завершается перед выходом из `start()`.

## Протокол

Одно соединение содержит один запрос и один ответ. Сообщение состоит из:

1. Четырёх байтов длины JSON в байтах: положительный `int`, big-endian.
2. Указанного количества байтов JSON в UTF-8.

Максимальный размер JSON — 8 МиБ. `readFully()` читает сообщение целиком,
даже если TCP доставляет его частями.

Пример запроса удаления плана:

```json
{
  "version": 1,
  "service": "example.PlanService",
  "method": "delete",
  "parameterTypes": ["long"],
  "arguments": [10]
}
```

`service` — полное имя зарегистрированного интерфейса.
`parameterTypes` содержит имена объявленных типов параметров, полученные через
`Class.getName()`. Поэтому перегрузки различаются и при аргументах `null`.
У метода без параметров оба массива пустые.

Текущая версия протокола — `1`. Поле `version` обязательно. До вызова сервиса
сервер проверяет версию и при несовместимости возвращает ошибку протокола.

Успешный ответ:

```json
{"success": true, "result": null, "error": null, "errorType": null}
```

Ответ с ошибкой:

```json
{"success": false, "result": null, "error": "java.lang.IllegalArgumentException: Plan not found: 999", "errorType": "REMOTE"}
```

При несовместимой версии:

```json
{"success": false, "result": null, "error": "Unsupported protocol version: 2; expected 1", "errorType": "PROTOCOL"}
```

По `errorType` клиент выбирает исключение: `REMOTE` означает
`RpcRemoteException`, а `PROTOCOL` — `RpcProtocolException`.

Для `void` и результата `null` поле `result` равно `null`. Пропуск результата,
обрыв сообщения, некорректный JSON или несовместимый тип результата приводят
к `RpcProtocolException`.

Ошибка подключения или таймаут дают `RpcConnectionException`. Отсутствующий
сервис, метод, неверные аргументы и исключение внутри сервиса дают
`RpcRemoteException`. После ошибки запроса сервер принимает следующие вызовы.

## Устройство

- `RpcClient` создаёт прокси и отправляет вызовы на сервер.
- `RpcServer` хранит сервисы и кэш методов их интерфейсов.
- `RpcService` помечает интерфейсы для автоматической регистрации.
- `Protocol` читает и записывает сообщения с длиной и JSON.
- `JsonTypes` восстанавливает значения по типам, объявленным в методе.

`List<T>` собирается в `ArrayList`, `Map<String, T>` — в `LinkedHashMap`.
Для каждого элемента снова вызывается преобразование по его типу.
Обычные объекты, в том числе `record TrainingPlan`, создаёт Jackson. Поэтому
элементы `List<TrainingPlan>` имеют тип `TrainingPlan` и на клиенте, и на сервере.

При регистрации сервер один раз получает методы интерфейса, включая
унаследованные, и сохраняет их вместе с generic-типами параметров.
Ключ кэша — имя метода и список объявленных типов параметров. У каждого
сервиса свой кэш, поэтому перегрузки и одноимённые методы разных сервисов
различаются. Во время запроса метод берётся из `Map`.

Один удалённый вызов проходит так:

1. Обработчик прокси получает метод и его аргументы.
2. Клиент отправляет версию, имя сервиса, имя метода, типы параметров и аргументы.
3. Сервер проверяет версию, берёт метод из кэша и восстанавливает аргументы по его типам.
4. `Method.invoke()` вызывает реализацию. Результат или ошибка отправляются клиенту.
5. Клиент восстанавливает результат по `getGenericReturnType()` или выбрасывает исключение.

## Тесты

```shell
mvn test
```

`RpcTest` проверяет вызовы, DTO и коллекции, `null`, перегрузки, ошибки,
таймаут, локальные методы прокси, регистрацию и освобождение порта.
`ProtocolTest` проверяет чтение частями, повреждённые и несовместимые ответы,
неверные запросы, запрет вызова методов за пределами интерфейса и несовместимые версии.
`RegistrationTest` проверяет автоматическую регистрацию помеченных интерфейсов,
в том числе унаследованных, и ограничения регистрации.

`PlanServiceTest` проверяет спортивный сервис через TCP: исходные планы,
наследуемые методы, типы элементов расписания, добавление, удаление и ошибку
при запросе отсутствующего расписания.

Калькулятор и `UserService` из условия находятся только в `src/test/java/rpc/TestServices.java`.
Они проверяют работу фреймворка с другими интерфейсами, включая `User`,
`List<User>` и `Map<String, User>`.
